Mülakatta Sorulan Ama Seni İyi Bir Yazılımcı Yapmayan 20 Bilgi

dotnet·9 Nisan 2026·~17 dk okuma

Yazılım mülakatlarında bazı konular çok sık sorulur. Bu konuların bir kısmı gerçekten temeldir ve bilinmesi gerekir. Ama bir kısmı da vardır ki, mülakatta güzel görünür; gerçek projede ise tek başına çok az şey ifade eder.

Sorun şu değildir: Bu bilgiler gereksizdir.

Sorun şudur: Bu bilgiler, olduklarından daha önemli sanılabilir.

Birçok aday, bu tip sorulara ezber cevap verdiğinde konuyu bildiğini düşünür. Oysa yazılımda asıl önemli olan, kavramın adını söylemek değil, onu doğru yerde ve doğru şekilde kullanabilmektir. Bu yazıda, mülakatlarda sık geçen ama pratikte ancak doğru bağlamda anlam kazanan bazı bilgileri daha net ve doğru şekilde ele alacağım.

Bilmek ile kullanabilmek aynı şey değildir

Mülakatta bir kavramı tanımlamak çoğu zaman kolaydır. Asıl zor olan, o kavramın ne zaman işe yaradığını, ne zaman yaramadığını ve neyi çözmek için var olduğunu bilmektir.

Burada iki temel ayrım var:

Teorik bilgi: Bir şeyin ne olduğunu anlatır.
Pratik bilgi: O şeyin hangi durumda, neden ve nasıl kullanılması gerektiğini gösterir.

Yazılımda değerli olan, çoğu zaman ikinci kısımdır.

1. HTTP status code bilmek, iyi API tasarlamak değildir

HTTP status code’lar, bir isteğe verilen cevabın sonucunu anlatan sayısal kodlardır. Örneğin:

  • 200 başarı,
  • 400 hatalı istek,
  • 401 kimlik doğrulama yok,
  • 403 yetki yok,
  • 404 bulunamadı,
  • 500 sunucu hatası anlamına gelir.

Bunları bilmek önemlidir. Ama yalnızca sayıların anlamını ezberlemek yeterli değildir. Gerçek mesele, hangi durumda hangi kodun dönmesi gerektiğini bilmektir.

Örneğin kullanıcı hatası ile sistem hatası aynı şey değildir. Kullanıcının yanlış veri göndermesi ile sunucunun beklenmeyen şekilde çökmesi aynı cevapla dönmemelidir.

Aşağıdaki örnekte bunun basit bir kullanımını görebilirsin:

using Microsoft.AspNetCore.Mvc; // API controller özelliklerini kullanmak için gerekli namespace

namespace DemoApi.Controllers // Controller sınıfını düzenli tutmak için namespace tanımı
{
    [ApiController] // Bu sınıfın bir API controller olduğunu belirtir
    [Route("api/[controller]")] // Endpoint adresinin nasıl oluşacağını belirler
    public class OrdersController : ControllerBase // API davranışı için ControllerBase'ten türetilir
    {
        [HttpPost] // Bu metodun POST isteği karşılayacağını söyler
        public IActionResult CreateOrder([FromBody] CreateOrderRequest request) // İstek gövdesinden veri alır
        {
            if (request == null) // İstek boş mu diye kontrol eder
            {
                return BadRequest("İstek boş olamaz."); // 400 döner, çünkü istek hatalıdır
            }

            if (request.Amount <= 0) // İş kuralına aykırı bir tutar mı diye bakar
            {
                return UnprocessableEntity("Tutar sıfırdan büyük olmalıdır."); // 422 döner, çünkü veri biçimsel olarak doğru ama anlam olarak geçersizdir
            }

            return Ok("Sipariş oluşturuldu."); // İşlem başarılıysa 200 döner
        }
    }

    public class CreateOrderRequest // Gelen isteği temsil eden model
    {
        public decimal Amount { get; set; } // Sipariş tutarını tutan alan
    }
}

Buradaki doğru bakış şudur:
Status code bilmek önemlidir, ama asıl önemli olan doğru cevabı doğru sebeple dönebilmektir.

2. async ve await bilmek, asenkron düşünmek anlamına gelmez

Bu konu mülakatlarda çok sık sorulur. Çoğu zaman adaylar “asenkron çalışmayı sağlar” gibi kısa cevaplar verir. Bu cevap yanlış değildir, ama eksiktir.

Önce terimi netleştirelim:

Asenkron, bir iş sürerken ana akışın tamamen durmaması demektir.
 Yani bir işlem devam ederken sistem başka işleri de sürdürebilir.

Burada önemli bir ayrım vardır:

  • I/O bound: Ağ, veritabanı, disk gibi dış kaynak bekleyen işler
  • CPU bound: İşlemciyi yoğun kullanan işler

async ve await özellikle I/O bound işlerde anlamlıdır. Çünkü bu tür işlerde thread’i boşa çıkarmaya yardımcı olur. Ama bu, her zaman performans artışı sağlar demek değildir. Yanlış yerde kullanılırsa faydasız kalabilir.

Bir noktayı net söylemek gerekir:
 await, metodu bir sonucun tamamlanmasını bekleyecek şekilde duraklatır; fakat bu bekleme sırasında thread’in gereksiz yere bloke edilmesini engeller.
 Doğrusu budur.

Aşağıdaki örneğe bakalım:

using System.Net.Http; // HTTP istekleri atabilmek için gerekli namespace
using System.Threading.Tasks; // Task tabanlı asenkron yapı için gerekli namespace

namespace DemoApp.Services // Servis sınıflarını düzenli tutmak için namespace
{
    public class ProductService // Ürün verilerini yöneten servis sınıfı
    {
        private readonly HttpClient _httpClient; // Dış servislere istek atmak için kullanılacak HttpClient

        public ProductService(HttpClient httpClient) // HttpClient bağımlılığını dışarıdan alıyoruz
        {
            _httpClient = httpClient; // Gelen nesneyi alanımıza kaydediyoruz
        }

        public async Task<string> GetProductsAsync() // Asenkron çalışan bir metod tanımlıyoruz
        {
            var response = await _httpClient.GetAsync("https://example.com/api/products"); // HTTP isteği atıyoruz ve cevabı tamamlanana kadar bekliyoruz
            var content = await response.Content.ReadAsStringAsync(); // Dönen içeriği asenkron şekilde okuyoruz
            return content; // İçeriği dışarı döndürüyoruz
        }
    }
}

Bu örnekte doğru bilgi şudur:
await yalnızca “beklemek” değildir; asenkron bir işlemin tamamlanmasını verimli şekilde bekleme yöntemidir.
Ama bu, her yerde kullanılması gerektiği anlamına gelmez. İşin türüne göre karar vermek gerekir.

3. static bilmek, doğru tasarım kurmak değildir

static kelimesi de çok sorulur. Teknik olarak static, bir üyenin sınıfa ait olduğunu, nesneye ait olmadığını ifade eder.

Yani:

  • Nesne oluşturmadan erişilebilir,
  • Sınıfın ortak davranışı gibi düşünülebilir,
  • Her durumda ayrı örnek oluşturulmasını engeller.

Bu bilgi tek başına faydalıdır. Ama birçok kişi static kullanmayı avantaj sanır. Oysa iş mantığını static yapmak çoğu zaman test etmeyi zorlaştırır, bağımlılıkları gizler ve esnekliği azaltır.

Aşağıdaki örnek yardımcı bir işlem için uygundur:

using System; // DateTime gibi temel tipleri kullanmak için namespace

namespace DemoApp.Helpers // Yardımcı sınıfları tutmak için namespace
{
    public static class DateHelper // Static class: nesne oluşturmadan kullanılabilir
    {
        public static string GetTodayText() // Static metod: sınıfa bağlı çalışır
        {
            var today = DateTime.Now; // Şu anki tarihi ve saati alıyoruz
            return today.ToString("yyyy-MM-dd"); // Tarihi okunabilir bir formata çeviriyoruz
        }
    }
}

Burada doğru bilgi şu:
static, sınıfa ait üyeleri tanımlar.
Ama bu, onu her sorun için doğru seçim yapmaz. Özellikle iş mantığı içeren sınıflarda dikkatli olmak gerekir.

4. ref, out, in bilmek, bunları doğru yerde kullanmak demek değildir

Bu anahtar kelimeler mülakatlarda sık sorulur. Çünkü dilin alt seviyesindeki davranışları anlamayı ölçer.

Kısaca doğru anlamları:

  • ref: Değişken referansla geçilir, önceden değer verilmiş olmalıdır
  • out: Değişken referansla geçilir, metod içinde değer atanması zorunludur
  • in: Değişken readonly referans olarak geçilir, yani metod içinde değiştirilmemelidir

Bunları bilmek teknik açıdan önemlidir. Ama gerçek projede çoğu zaman daha sade yöntemler tercih edilir. Çünkü bu anahtar kelimeler kodun okunmasını zorlaştırabilir.

Örnek:

using System; // Temel tipleri kullanmak için namespace

namespace DemoApp.Utils // Yardımcı sınıflar için namespace
{
    public class NumberParser // Sayı dönüştürme işlemlerini yapan sınıf
    {
        public bool TryParseInt(string input, out int result) // out parametresi ile sonucu dışarı veriyoruz
        {
            return int.TryParse(input, out result); // Metin sayıya çevrilebiliyorsa true, çevrilemiyorsa false döndürür
        }
    }
}

Burada doğru bilgi şudur:
out, metodun bir sonucu dışarı vermesi için kullanılır.
Ama bu, her zaman en iyi yöntem değildir. Çoğu durumda normal dönüş değeri daha temiz ve okunabilir olur.

5. Task, Thread, Parallel aynı şey değildir

Bu konu çok karıştırılır. Mülakatta da sık sorulur.

Doğru farklar şunlardır:

  • Thread: İşletim sistemi seviyesinde çalışan yürütme birimidir
  • Task: Genellikle bir işi temsil eden üst seviye soyutlamadır
  • Parallel: İşin aynı anda birden fazla parçaya dağıtılmasına odaklanır

Burada kritik nokta şudur:
 Task, Thread ile birebir aynı şey değildir.
 Bir Task, bazen thread üzerinde çalışır, bazen planlama mekanizması onu başka şekilde yürütür. Yani Task daha üst seviyede bir yapıdır.

Basit örnek:

using System.Threading.Tasks; // Task kullanabilmek için gerekli namespace

namespace DemoApp.Workers // Çalışma sınıflarını tutan namespace
{
    public class ReportWorker // Rapor oluşturma işini yapan sınıf
    {
        public async Task GenerateReportAsync() // Asenkron bir iş tanımlıyoruz
        {
            await Task.Delay(1000); // Örnek olarak bir saniyelik bekleme simülasyonu yapıyoruz
        }

        public void DoParallelWork() // Paralel işleme örneği gösteren metod
        {
            Parallel.For(0, 10, i => // 0'dan 9'a kadar işlemleri paralel çalıştırıyoruz
            {
                Console.WriteLine(i); // Her iterasyonda sayıyı ekrana yazıyoruz
            });
        }
    }
}

Burada doğru bilgi şu:
Task, “thread ile aynı şey” değildir.
Ayrıca Parallel, her zaman kullanılacak bir araç da değildir. İşin türüne göre seçilmelidir.

6. Design pattern adını bilmek, problemi çözmek anlamına gelmez

Design pattern, tekrar eden tasarım problemleri için geliştirilmiş genel çözüm kalıbıdır.
 Yani bir tür “hazır düşünme modeli” gibidir.

Mülakatta Singleton, Factory, Strategy, Observer gibi isimleri saymak kolaydır. Ama bunları yanlış yerde kullanmak, sistemi sadeleştirmek yerine karmaşıklaştırabilir.

Örneğin bazı adaylar pattern görünce etkilenir ama sorunun gerçekten o pattern’i gerektirip gerektirmediğini sorgulamaz. İşte burada ezber devreye girer.

Doğru düşünce şudur:
Pattern, problemi çözmek için vardır. Problem yoksa pattern zorla eklenmez.

7. SOLID prensiplerini ezberlemek, iyi tasarım yapmak değildir

SOLID, yazılım tasarımını daha sürdürülebilir hale getirmeyi amaçlayan beş temel prensip grubudur.

Açılımları şunlardır:

  • Single Responsibility
  • Open/Closed
  • Liskov Substitution
  • Interface Segregation
  • Dependency Inversion

Bunları bilmek önemlidir. Ama çoğu kişi yalnızca isimlerini bilir. Oysa asıl mesele, bu prensiplerin neden var olduğunu anlamaktır.

Özellikle şu noktayı doğru okumak gerekir:
Single Responsibility, “bir sınıf yalnızca bir metot içersin” demek değildir.
Doğrusu, bir sınıfın değişme nedeninin mümkün olduğunca tek bir eksende tutulmasıdır.

Bu çok önemli bir farktır. Ezber bilgi ile gerçek anlayış arasındaki çizgi tam burada başlar.

8. IEnumerable, IQueryable, List farkını bilmek, sorgu davranışını anlamak demek değildir

Bu konu .NET mülakatlarının klasikleri arasındadır.

Kısaca doğru tanımlar:

  • List: Bellekte tutulan somut koleksiyondur
  • IEnumerable: Koleksiyon üzerinde sırayla gezinmeyi sağlayan arayüzdür
  • IQueryable: Sorgunun dış kaynakta, örneğin veritabanında çalıştırılmasına izin veren yapıdır

Buradaki en kritik fark, IQueryable’ın sorguyu mümkün olduğunda kaynağa taşıyabilmesidir. Yani sorgunun tamamı uygulama belleğinde değil, veritabanı tarafında çalışabilir. Bu performans açısından çok önemlidir.

using System.Collections.Generic; // List gibi koleksiyonları kullanmak için namespace
using System.Linq; // Where, Select gibi sorgu metotları için namespace

namespace DemoApp.Data // Veri işlemleri için namespace
{
    public class ProductRepository // Ürün verilerini yöneten repository sınıfı
    {
        public List<string> GetProductsList() // Somut bir liste döndüren metod
        {
            return new List<string> // Bellekte gerçek bir liste oluşturuyoruz
            {
                "Kalem", // İlk ürün
                "Defter", // İkinci ürün
                "Silgi" // Üçüncü ürün
            };
        }

        public IEnumerable<string> GetEnumerableProducts() // IEnumerable döndüren metod
        {
            return GetProductsList().Where(x => x.Length > 5); // Bellekteki veri üzerinde filtreleme yapıyoruz
        }
    }
}

Burada doğru bilgi şu:
List, IEnumerable ve IQueryable aynı şey değildir.
Özellikle veri kaynağı büyükse, bu fark doğrudan performansı etkiler.

9. “var“ kullanmak kodu daha modern yapmaz

Bu konu mülakatlarda genelde basit geçilir ama aslında önemli bir okuma (readability) meselesidir.

Kısaca doğru tanım:

var: Değişkenin tipini derleyicinin otomatik çıkarmasını sağlar

Yani şu iki kullanım teknik olarak aynıdır:

var name = "Test"; // Derleyici bunun string olduğunu anlar
string name2 = "Test"; // Açık şekilde string olarak tanımlanır

Peki problem nerede başlıyor?

Şu örneğe bakalım:

var result = GetData(); // GetData ne döndürüyor? Liste mi? Tek obje mi? Null olabilir mi?

Burada kodu okuyan kişi için belirsizlik oluşur. Çünkü result değişkeninin tipi açık değildir.

Daha açık yazım:

List<string> result = GetData(); // Tip artık net şekilde anlaşılır

Burada doğru bilgi şu:

  • var kullanmak performans kazancı sağlamaz
  • var, okunabilirliği artırıyorsa iyidir, azaltıyorsa kötüdür

Kısa not:
Modern kod yazmak, kısa kod yazmak değildir. Okunabilir kod yazmaktır.

10. delegate, Func, Action bilmek, davranışı anlamak demek değildir

Bu konu mülakatta çok “teorik” sorulur ama aslında çok güçlü bir yapıdır.

Kısaca doğru tanımlar:

  • delegate: Metot referansı tutan yapıdır
  • Action: Geri dönüş değeri olmayan hazır delegate
  • Func: Geri dönüş değeri olan hazır delegate

Ama asıl önemli olan şudur:
Metodu parametre olarak geçebilmek

Örnek:

using System; // Action ve Func kullanmak için gerekli namespace

namespace DemoApp.Services
{
    public class MessageService
    {
        public void Process(string message, Action<string> logger) // Dışarıdan bir davranış alıyoruz
        {
            // Gelen mesajı dışarıdan verilen metoda gönderiyoruz
            logger(message);
        }
    }
}

Kullanım:

var service = new MessageService();

// Logger davranışını dışarıdan veriyoruz
service.Process("Merhaba", msg =>
{
    Console.WriteLine($"Log: {msg}"); // Gelen mesajı logluyoruz
});

Burada önemli olan:

  • Logger metodu sabit değil
  • Dışarıdan değiştirilebilir

Burada doğru bilgi şu:

Action ve Func, kodu esnek hale getirmek için kullanılır.
Sadece “geri dönüşü var/yok” demek konunun %20’sidir.

11. Exception yönetimi bilmek, hata yönetimi yapmak değildir

Mülakatta genelde şu sorulur:

try-catch biliyor musun?

Ama gerçek soru şu olmalı:

Hata olduğunda sistem nasıl davranacak?

Basit örnek:

try
{
    var data = GetData(); // Veri çekiyoruz
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message); // Sadece ekrana yazdırıyoruz
}

Bu kod çalışır. Ama gerçek hayatta yetersizdir.

Daha doğru yaklaşım:

try
{
    var data = GetData(); // Veri çekme işlemi
}
catch (Exception ex)
{
    // Hata detayını logluyoruz
    Console.WriteLine($"Hata oluştu: {ex.Message}");

    // Kullanıcıya anlamlı cevap dönüyoruz
    throw new ApplicationException("İşlem sırasında hata oluştu."); 
}

Daha profesyonel yaklaşım:

  • merkezi log sistemi (Serilog, ELK vs.)
  • kullanıcıya teknik hata göstermemek

Burada doğru bilgi şu:

Exception handling sadece hatayı yakalamak değildir.
Hatanın yönetilmesidir.

12. null kontrolü bilmek, null-safe sistem kurmak değildir

null konusu basit görünür ama en çok bug çıkaran konulardan biridir.

Klasik yaklaşım:

if (user != null)
{
    Console.WriteLine(user.Name);
}

Bu doğru ama yüzeysel. Asıl problem şudur: Neden null geldi?

Daha iyi yaklaşım:

if (user == null)
{
    throw new Exception("User bulunamadı"); // Problemi erken yakalıyoruz
}

Console.WriteLine(user.Name); // Artık güvenli

Modern C# yaklaşımı:

Console.WriteLine(user?.Name); // user null ise hata vermez

Ama dikkat: Bu, problemi çözmez. Sadece hatayı gizler.

Burada doğru bilgi şu: Null kontrolü yazmak çözüm değildir. Null oluşmasını anlamak ve yönetmek olması gereken çözüm.

13. using bilmek, kaynak yönetimini anlamak değildir

Mülakatta genelde şöyle anlatılır:

using blok bitince nesne kapanır

Ama asıl konu şudur:
Dispose nedir?

Örnek:

using (var file = new StreamWriter("test.txt")) // Dosya açıyoruz
{
    file.WriteLine("Merhaba"); // Dosyaya yazıyoruz
} // Burada Dispose çağrılır ve dosya kapanır

Bu ne sağlar?

  • dosya kilitli kalmaz
  • bellek serbest bırakılır
  • resource leak oluşmaz

Aynı şeyi manuel yazarsak:

var file = new StreamWriter("test.txt");

try
{
    file.WriteLine("Merhaba");
}
finally
{
    file.Dispose(); // Kaynağı manuel temizliyoruz
}

Burada doğru bilgi şu: using, sadece sözdizimi değildir. Kaynakların doğru zamanda serbest bırakılmasını garanti eder.

14. DI bilmek yetmez, lifetime bilmek gerekir

Dependency Injection herkesin bildiği bir konu. Ama kritik nokta genelde kaçırılır:

Lifetime (yaşam süresi)

Kısaca:

  • Transient → her istekte yeni nesne
  • Scoped → request boyunca tek nesne
  • Singleton → uygulama boyunca tek nesne

Örnek:

services.AddSingleton<MyService>(); // Tek instance
services.AddScoped<MyService>(); // Request başına
services.AddTransient<MyService>(); // Her kullanımda yeni

En kritik hata:

public class MySingletonService
{
    private readonly MyScopedService _scopedService; // HATALI kullanım

    public MySingletonService(MyScopedService scopedService)
    {
        _scopedService = scopedService;
    }
}

Neden hatalı?

  • Singleton uzun yaşar
  • Scoped kısa yaşar

Bu durumda: Scoped nesne yanlış lifecycle’da tutulur

Burada doğru bilgi şu: DI sadece bağımlılığı çözmek değildir. Nesnelerin yaşam süresini doğru yönetmektir.

15. LINQ bilmek, çalışma zamanını anlamak değildir

LINQ çok güçlü ama yanlış kullanılırsa performans düşürür.

En kritik kavram: Deferred Execution (ertelenmiş çalışma)

Örnek:

var numbers = new List<int> { 1, 2, 3, 4 };

var query = numbers.Where(x => x > 2); // Henüz çalışmadı

numbers.Add(5); // Listeyi değiştirdik

foreach (var item in query) // Burada çalışır
{
    Console.WriteLine(item); // 3,4,5 gelir
}

Neden 5 geldi?

Çünkü:

  • sorgu başta çalışmadı
  • foreach sırasında çalıştı

Eğer hemen çalışmasını istersek:

var query = numbers.Where(x => x > 2).ToList(); // Anında çalışır

Burada doğru bilgi şu:

LINQ sadece sorgu yazmak değildir. Ne zaman çalıştığını bilmek gerekir.

16. Authentication vs Authorization farkı

Çok klasik ama kritik.

  • Authentication → kullanıcı kim?
  • Authorization → ne yapabilir?

Örnek:

[Authorize] // Yetki kontrolü yapar
public IActionResult GetData()
{
    return Ok("Veri");
}

Ama şu senaryoyu düşün:

  • kullanıcı login oldu (authentication OK)
  • ama admin değil

Eğer authorization doğru kurulmazsa:
 → kullanıcı erişmemesi gereken yere erişir

Burada doğru bilgi şu: Kimliği doğrulamak yetmez. Yetkisini de doğru kontrol etmek gerekir.

17. Config yönetimi bilmek, ortam yönetmek değildir

Gerçek projelerde en kritik konulardan biridir.

Örnek config:

{
  "ConnectionStrings": {
    "Default": "Server=DEV_DB"
  }
}

Prod ortamda:

{
  "ConnectionStrings": {
    "Default": "Server=PROD_DB"
  }
}

Bu ayrımı yönetmezsen:

  • yanlış DB’ye bağlanırsın
  • canlı sistemi bozarsın

Burada doğru bilgi şu: Config sadece ayar değildir. Ortam davranışını belirler.

18. Garbage Collector (GC) bilmek, performans anlamak değildir

Kısa doğru tanım:

  • Garbage Collector (GC): Kullanılmayan nesneleri bellekten temizleyen otomatik mekanizmadır

Ama burada kritik yanlış anlama şu:

“Çok nesne üretirsem GC temizler, sorun yok”

Bu yanlış.

GC nasıl çalışır (basitleştirilmiş):

.NET’te GC generational (nesil bazlı) çalışır:

  • Gen 0 → kısa ömürlü nesneler (en sık temizlenen)
  • Gen 1 → orta ömürlü
  • Gen 2 → uzun ömürlü (en pahalı temizleme)

Yani:

  • küçük ve kısa ömürlü nesneler ucuzdur
  • uzun yaşayan nesneler pahalıdır

Problem nerede başlıyor?

Şu örneğe bakalım:

for (int i = 0; i < 1000000; i++)
{
    var obj = new object(); // Her iterasyonda yeni nesne oluşturuyoruz
}

İlk bakışta:

  • “GC temizler zaten” diyebilirsin

Ama gerçekte:

  • sürekli allocation (bellek ayırma) yapılır
  • GC çok sık tetiklenir
  • CPU zamanı GC’ye gider

Asıl önemli kavram: Allocation maliyeti

GC sadece temizleme değildir.
 Asıl maliyet çoğu zaman allocation’dadır.

Yani:

  • Nesne oluşturmak ucuz değildir
  • Çok fazla oluşturmak → GC baskısı (memory pressure)

Daha gerçekçi problem:

var list = new List<string>();

for (int i = 0; i < 100000; i++)
{
    list.Add(i.ToString()); // Her seferinde yeni string oluşturuluyor
}

Burada:

  • sürekli yeni string üretiliyor
  • heap doluyor
  • GC devreye giriyor

Ama daha iyi yaklaşım olabilir:

  • pooling
  • reuse
  • gereksiz allocation’dan kaçınmak

Kritik nokta: GC performans düşürmez. Yanlış kullanım GC’yi zorlar, o da performansı etkiler.

GC ile ilgili doğru düşünce şu olmalı:

  • GC’yi “optimize etmeye” çalışma
  • Allocation’ı azaltmaya çalış
  • Uzun yaşayan nesneleri kontrol et
  • Büyük objelerden kaçın (LOH — Large Object Heap)

LOH (kısa ama kritik bilgi)

  • 85KB üzeri objeler → LOH’e gider
  • daha zor temizlenir
  • fragmentation (parçalanma) yaratır

Bu yüzden büyük array / string üretimi kritik olabilir.

19. interface bilmek, abstraction (soyutlama) yapmak demek değildir

Bu konu mülakatların vazgeçilmezidir.

interface: Bir sınıfın ne yapacağını tanımlar, nasıl yapacağını değil

Yani:

public interface IPaymentService // Ödeme işlemi yapabilen bir yapı tanımlıyoruz
{
    void Pay(decimal amount); // Nasıl değil, ne yapacağı tanımlanır
}

Implementasyon:

public class CreditCardPaymentService : IPaymentService // Interface'i implemente ediyoruz
{
    public void Pay(decimal amount)
    {
        Console.WriteLine("Kredi kartı ile ödeme alındı"); // Gerçek davranış burada
    }
}

Buraya kadar herkes biliyor.

Ama asıl problem şurada:

public class PaymentManager
{
    private readonly CreditCardPaymentService _service; // Interface yerine concrete class kullanılıyor

    public PaymentManager(CreditCardPaymentService service)
    {
        _service = service;
    }
}

Bu ne demek?

  • Kod interface yazılmış gibi görünüyor
  • Ama aslında bağımlılık hala somut sınıfa

Doğru kullanım:

public class PaymentManager
{
    private readonly IPaymentService _service; // Interface'e bağımlıyız

    public PaymentManager(IPaymentService service)
    {
        _service = service;
    }
}

Burada ne kazandık?

  • farklı ödeme yöntemleri kolayca eklenir
  • test yazmak kolaylaşır
  • sistem esnek olur

Burada doğru bilgi şu:

Interface yazmak abstraction değildir.
Abstraction, bağımlılığı soyutlamaya taşımaktır.

20. “Clean Code” bilmek, temiz kod yazmak değildir

Bu mülakatta direkt sorulmaz ama dolaylı olarak sürekli ölçülür.

Çoğu kişi şunu sanır:

  • değişken isimleri düzgün → clean code
  • kısa metod → clean code

Bunlar doğru ama eksik.

Kötü örnek:

public void Process()
{
    var d = GetData(); // d ne?
    var r = d.Where(x => x.IsActive).ToList(); // r ne?
    
    foreach (var i in r)
    {
        if (i.Amt > 1000)
        {
            Send(i); // Send ne yapıyor?
        }
    }
}

Bu kod çalışır. Ama okunmaz.

Daha temiz hali:

public void ProcessActiveHighValueOrders()
{
    var orders = GetData(); // Tüm siparişleri alıyoruz

    var activeOrders = orders
        .Where(order => order.IsActive) // Aktif siparişleri filtreliyoruz
        .ToList(); // Listeye çeviriyoruz

    foreach (var order in activeOrders)
    {
        if (order.Amount > 1000) // Yüksek tutarlı siparişleri kontrol ediyoruz
        {
            SendHighValueOrder(order); // Özel işlem uyguluyoruz
        }
    }
}

Fark ne?

  • isimler anlamlı
  • niyet açık
  • okuyan kişi tahmin yapmak zorunda değil

Ama asıl kritik fark şu:

Clean Code = Okunabilir + Anlaşılabilir + Tahmin edilebilir kod

En önemli nokta: Clean Code sadece stil değildir.

Aynı zamanda:

  • bakım maliyeti
  • hata yapma ihtimali
  • ekip içi iletişim

demektir.

Neden bu bilgiler mülakatta sık sorulur?

Çünkü kısa sürede temel seviyeyle pratik seviyeyi ayırmak için işe yararlar. Adayın:

  • kavramı bilip bilmediğini,
  • dilin temel mekaniklerini anlayıp anlamadığını,
  • basit senaryolarda hata yapıp yapmadığını
     görmeye yardımcı olurlar.

Ama burada tuzak şudur:
Mülakat sorusunda doğru cevap vermek, gerçek projede doğru karar vermekle aynı şey değildir.

Asıl değer nerede ortaya çıkar?

Gerçek değeri yaratan şeyler genelde daha sade ama daha önemlidir:

  • doğru problemi görmek
  • doğru soruyu sormak
  • sade çözüm kurmak
  • bakım maliyetini düşünmek
  • performans etkisini sezmek
  • test edilebilir kod yazmak
  • hata oluşunca doğru yeri bulmak

Yani önemli olan, kavramı tanımak değil; onu sistem içinde doğru yere koyabilmektir.

Sonuç

Mülakatta geçen ama gerçekte işe yaramayan bilgiler tamamen değersiz değildir. Fakat onları merkeze koymak yanıltıcı olur.
Status code bilmek önemlidir, ama API tasarlamak başka bir iştir.
async/await bilmek önemlidir, ama doğru yerde kullanmak daha önemlidir. static, ref, out, Task, Thread, design pattern’ler ve SOLID prensipleri de böyledir.

Hepsi araçtır. Ama araçları bilmek ile onları doğru amaçla kullanmak arasında ciddi fark vardır.

Yazılımda güçlü olmayı sağlayan şey, çok kavram bilmekten çok; hangi kavramın hangi sorunu çözdüğünü anlayabilmektir.
