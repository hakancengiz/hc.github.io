Repository Pattern Nedir? Gerçekte Ne İşe Yarar?

csharp·12 Mayıs 2026·~3 dk okuma

Repository Pattern, en basit tanımıyla:

Veri erişim (data access) kodunu, iş mantığından (business logic) ayıran bir tasarım yaklaşımıdır.

Buradaki bazı terimleri netleştirelim:

  • Data Access (Veri Erişimi): Veritabanına gidip veri okuma/yazma işlemleri
  • Business Logic (İş Mantığı): Uygulamanın karar verme kısmı (örneğin “kullanıcı aktif mi?” gibi kurallar)

Neden Repository Pattern Kullanılır?

Bir projede doğrudan şöyle kod yazarsan:

var user = db.Users.First(x => x.Id == 1);

Bu kod:

  • Veritabanına bağımlıdır
  • Test edilmesi zordur
  • Kod tekrarına yol açar

Repository Pattern bu bağımlılığı azaltır.

Temel Mantık

Repository Pattern şunu yapar:

  • Veritabanı detayını gizler
  • Uygulamaya sade bir arayüz (interface) sunar

Yani sen şunu dersin:

“Bana kullanıcıyı getir”
 Ama nasıl getirildiği önemli değildir

Adım Adım Uygulama

1. Entity (Veri Modeli)

public class User // Kullanıcıyı temsil eden sınıf
{
    public int Id { get; set; } // Kullanıcının benzersiz kimliği
    public string Name { get; set; } // Kullanıcının adı
    public bool IsActive { get; set; } // Kullanıcı aktif mi bilgisi
}

2. Repository Interface (Sözleşme)

Interface (arayüz), “ne yapılacağını” tanımlar ama “nasıl yapılacağını” söylemez.

public interface IUserRepository // Kullanıcı işlemleri için sözleşme
{
    User GetById(int id); // ID ile kullanıcı getirir
    List<User> GetActiveUsers(); // Aktif kullanıcıları getirir
    void Add(User user); // Yeni kullanıcı ekler
}

Interface:

  • Uygulamanın DB’den bağımsız olmasını sağlar
  • Mock (sahte veri) ile test yazmayı kolaylaştırır

3. Repository Implementation (Gerçek Kod)

Burada artık veritabanı ile konuşan kodu yazarız.

public class EfUserRepository : IUserRepository // Entity Framework kullanan repository
{
    private readonly AppDbContext _context; // Veritabanı bağlantısı

    public EfUserRepository(AppDbContext context) // Constructor (yapıcı metot)
    {
        _context = context; // Dışarıdan gelen context atanır
    }

    public User GetById(int id) // Kullanıcıyı ID ile getiren metot
    {
        return _context.Users // Users tablosuna erişilir
            .FirstOrDefault(x => x.Id == id); // ID eşleşen kullanıcı bulunur
    }

    public List<User> GetActiveUsers() // Aktif kullanıcıları getiren metot
    {
        return _context.Users // Users tablosuna erişilir
            .Where(x => x.IsActive) // Sadece aktif kullanıcılar filtrelenir
            .ToList(); // Sonuç listeye çevrilir
    }

    public void Add(User user) // Yeni kullanıcı ekleyen metot
    {
        _context.Users.Add(user); // Kullanıcı context'e eklenir
        _context.SaveChanges(); // Değişiklikler veritabanına yazılır
    }
}

4. Service Katmanında Kullanım

Artık business logic içinde direkt DB kullanmazsın.

public class UserService // İş mantığını yöneten sınıf
{
    private readonly IUserRepository _userRepository; // Repository bağımlılığı

    public UserService(IUserRepository userRepository) // Constructor injection
    {
        _userRepository = userRepository; // Repository atanır
    }

    public void CreateUser(string name) // Yeni kullanıcı oluşturma işlemi
    {
        var user = new User // Yeni kullanıcı nesnesi oluşturulur
        {
            Name = name, // Kullanıcı adı atanır
            IsActive = true // Varsayılan aktif yapılır
        };

        _userRepository.Add(user); // Repository üzerinden kaydedilir
    }
}

En Büyük Hata: IQueryable Dışarı Sızdırmak

Çok kritik bir konu.

Kötü kullanım:

public IQueryable<User> GetAll()

Neden kötü?

  • Query (sorgu) dış katmana taşar
  • Business layer DB bağımlı olur
  • Kontrol kaybolur

Doğru yaklaşım

public List<User> GetActiveUsers()

Yani:

Repository “ne yapılacağını” anlatır, “nasıl yapılacağını” saklar

Repository Pattern Ne Değildir?

Bu çok önemli.

Repository:

  • Generic CRUD makinesi değildir
  • Her tabloya birebir yazılmak zorunda değildir
  • Her projede şart değildir

Ne Zaman Kullanılmalı?

Kullan:

  • Orta/büyük projelerde
  • Test yazıyorsan
  • DB bağımlılığını azaltmak istiyorsan

Kullanma:

  • Küçük projede
  • Basit CRUD uygulamasında
  • Zaten ORM her şeyi çözüyorsa

Repository Pattern’in amacı:

“DB’yi gizlemek” değil
 “Domain dilini korumak”

Yani:

GetActiveUsers()

şu anlama gelir:

“Sistemde aktif kullanıcılar vardır ve bu bir iş kuralıdır”

Sonuç

Repository Pattern doğru kullanılırsa:

  • Kod okunabilir olur
  • Test yazmak kolaylaşır
  • DB bağımlılığı azalır

Ama yanlış kullanılırsa:

  • Gereksiz abstraction oluşur
  • Kod karmaşıklaşır
  • Performans düşebilir
