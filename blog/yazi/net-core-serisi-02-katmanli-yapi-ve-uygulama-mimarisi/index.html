Katmanlı Mimari Nedir?

Katmanlı mimari (Layered Architecture), bir yazılım projesini sorumluluklara göre bölerek yönetilebilir hale getiren yaklaşımdır.
 Amaç: kodun okunabilirliğini, test edilebilirliğini ve sürdürülebilirliğini artırmak.

Bir .NET Core uygulamasında bu yapı genellikle şu şekilde olur:

MyApp
 ┣ MyApp.API → Sunum (Presentation) katmanı
 ┣ MyApp.Business → İş kuralları (Service) katmanı
 ┣ MyApp.DataAccess → Veritabanı erişimi (Repository) katmanı
 ┗ MyApp.Entities → Modeller (Entity / DTO) katmanı

Katmanların Görevleri

1. Entities (Core Katmanı)

Uygulamanın temel modelleri burada yer alır.

// Entities/User.cs
// Kullanıcı bilgisini tutan temel model sınıfı
public class User
{
    // Her kullanıcı için benzersiz ID
    public int Id { get; set; }

    // Kullanıcının adı
    public string Name { get; set; } = string.Empty;

    // Kullanıcının e-posta adresi
    public string Email { get; set; } = string.Empty;
}

Bu katman, hiçbir dış bağımlılık içermez. Sadece veri yapısını tanımlar.

2. DataAccess Katmanı

Veritabanı işlemleri bu katmanda yapılır. Entity Framework Core veya Dapper gibi araçlar burada kullanılır.

// DataAccess/Repositories/UserRepository.cs
// Kullanıcı verilerini veritabanından alan repository sınıfı
public class UserRepository : IUserRepository
{
    // EF Core DbContext nesnesi (veritabanı bağlantısını temsil eder)
    private readonly AppDbContext _context;

    // Constructor'da bağımlılık olarak DbContext enjekte edilir
    public UserRepository(AppDbContext context)
    {
        _context = context;
    }

    // Tüm kullanıcıları veritabanından asenkron şekilde getirir
    public async Task<List<User>> GetAllAsync()
    {
        // EF Core üzerinden "Users" tablosundaki tüm kayıtları çeker
        return await _context.Users.ToListAsync();
    }
}

Bu katman, sadece veriyle ilgilenir.
İş kuralı (örneğin “e-posta kontrolü”) burada yazılmaz.

3. Business Katmanı

Tüm iş kuralları burada tanımlanır.
Repository’den gelen veriler üzerinde iş mantığı uygulanır.

// Business/Services/UserService.cs
// Kullanıcıyla ilgili iş kurallarını yöneten servis sınıfı
public class UserService : IUserService
{
    // Repository arayüzü (interface) üzerinden veri erişimi yapılır
    private readonly IUserRepository _userRepository;

    // Constructor Injection yöntemiyle repository enjekte edilir
    public UserService(IUserRepository userRepository)
    {
        _userRepository = userRepository;
    }

    // Aktif kullanıcıları (e-posta adresi dolu olanlar) döndürür
    public async Task<List<User>> GetActiveUsersAsync()
    {
        // Tüm kullanıcıları repository’den alır
        var users = await _userRepository.GetAllAsync();

        // E-postası boş olmayan kullanıcıları filtreler
        return users.Where(u => !string.IsNullOrEmpty(u.Email)).ToList();
    }
}

Burada dikkat edilmesi gereken nokta:
 → UserService, UserRepository’yi interface üzerinden kullanır.
 Bu sayede bağımlılıklar tersine çevrilmiş (Dependency Inversion) olur.

4. API (Presentation Katmanı)

Kullanıcıdan gelen istekleri (HTTP request) işler.
İş kurallarıyla doğrudan etkileşime geçmez, service katmanını çağırır.

// API/Controllers/UserController.cs
// API isteğini alan ve kullanıcı verisini dönen controller sınıfı
[ApiController]
[Route("api/[controller]")]
public class UserController : ControllerBase
{
    // Servis arayüzü (iş kurallarını temsil eder)
    private readonly IUserService _userService;

    // Dependency Injection ile IUserService alınır
    public UserController(IUserService userService)
    {
        _userService = userService;
    }

    // HTTP GET isteğini yakalar: /api/user
    [HttpGet]
    public async Task<IActionResult> GetUsers()
    {
        // Servisten aktif kullanıcıları alır
        var users = await _userService.GetActiveUsersAsync();

        // 200 OK durum kodu ile listeyi döner
        return Ok(users);
    }
}

Böylece controller yalnızca “istek–cevap” akışını yönetir.
İş kuralları veya veritabanı işlemleri burada yer almaz.

Dependency Injection (DI)

.NET Core, yerleşik bağımlılık enjeksiyonu (DI) desteğiyle gelir.
 Bu sayede katmanlar arasında gevşek bağlı bir yapı kurabiliriz.

Örnek:

// Program.cs
// Katmanlar arasındaki bağımlılıkların tanımlandığı yer

// Her HTTP isteğinde birer örnek oluşturulacak servisleri tanımlar
builder.Services.AddScoped<IUserRepository, UserRepository>();
builder.Services.AddScoped<IUserService, UserService>();

Burada:

  • IUserRepository → UserRepository
  • IUserService → UserService olarak eşleştirilir.

Artık bir Controller bu servisleri constructor aracılığıyla alabilir,
 .NET Core bunları otomatik olarak enjekte eder.

Service Lifetime Türleri

1. Transient

  • Her istekte yeni nesne oluşturur
  • Hafif işlemler, stateless servisler

2. Scoped

  • Her HTTP isteğinde bir örnek oluşturur
  • Web API servisleri için ideal

3. Singleton

  • Uygulama boyunca tek örnek kullanır
  • Konfigürasyon, cache servisleri

Örnek:

// Program.cs

// Transient: Her çağrıda yeni EmailSender nesnesi
builder.Services.AddTransient<IEmailSender, EmailSender>();

// Scoped: Her HTTP isteğinde yeni UserService nesnesi
builder.Services.AddScoped<IUserService, UserService>();

// Singleton: Uygulama süresince tek bir FileLogger nesnesi
builder.Services.AddSingleton<ILogger, FileLogger>();

Katmanlı Mimarinin Faydaları

  • Bağımsız geliştirme: Her katman ayrı test edilebilir.
  • Kolay değişiklik: UI değişse bile Business katmanı etkilenmez.
  • Sade yapı: Kodda net sorumluluk dağılımı vardır.
  • Yeniden kullanılabilirlik: Servisler başka projelerde de kullanılabilir.

Dikkat Edilmesi Gerekenler

  • Katmanlar arası bağımlılıklar doğru yönlü olmalı
     → DataAccess → Business → API
  • Controller’lar direkt olarak veritabanına erişmemeli
  • Business katmanında sadece iş mantığı bulunmalı
  • Gereksiz soyutlamalardan kaçınılmalı (örneğin 2 satırlık repository’yi interface ile sarmamak)

Temel prensip: her katman kendi işini yapmalı.

Böylece projeler:

  • Daha kolay test edilir,
  • Daha kolay genişletilir,
  • Ve uzun vadede bakım maliyetini azaltır.
