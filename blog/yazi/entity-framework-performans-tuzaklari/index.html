Entity Framework Performans Tuzakları

csharp·3 Mart 2026·~6 dk okuma

Kısa bir not: Aşağıda ele alınan başlıklar, gerçek proje deneyimlerinde sıklıkla karşılaşılan performans ve tasarım kaynaklı durumlara dayanmaktadır. Her bir bölümde önce ilgili problem çerçevelenmiş, ardından uygulanabilir çözüm yaklaşımı ve oluşabilecek örnek SQL çıktısı üzerinden teknik değerlendirme sunulmuştur.

1) N+1 problemi — döngü içinde veritabanına tekrar tekrar bakmak

Durum: Bir liste çekip, her öğe için ilişkili veriye ayrı ayrı erişildiğinde veritabanına çok sayıda sorgu gider. Bu, beklenenden yavaş çalışır.

Kötü örnek (N+1):

// Kötü örnek: N+1 riski
var customers = await db.Customers.ToListAsync(); // tüm müşteriler çekiliyor
foreach (var c in customers)
{
    // Eğer Orders lazy loading ile geliyorsa veya ayrı sorgu çağrısı oluyorsa
    var orderCount = await db.Orders.CountAsync(o => o.CustomerId == c.Id);
    Console.WriteLine($"{c.Id} -> {orderCount}");
}

Bu yaklaşımla veritabanına 1 + N (Customers için 1, her customer için 1) sorgu gidebilir.

Daha iyi yaklaşım — tek sorguda hesapla (projection):

// İyi: tek sorguda hesaplama (projection)
var users = await db.Users
    .Select(u => new {
        u.Id,
        u.Name,
        ActiveOrders = db.Orders.Count(o => o.UserId == u.Id && o.Status == "Active")
    })
    .AsNoTracking()
    .ToListAsync();

Bu LINQ ifadesinin SQL’e dönüştüğü tipik örnek (SQL Server için örnek):

SELECT [u].[Id], [u].[Name],
       (SELECT COUNT(*) FROM [Orders] AS [o] WHERE [o].[UserId] = [u].[Id] AND [o].[Status] = N'Active') AS [ActiveOrders]
FROM [Users] AS [u];

Bu yöntemle tek seferde gerekli aggregate hesap alınır; ağ trafiği ve round-trip sayısı azalır.

2) AsNoTracking() — sadece okuma yapıyorsanız faydası olur

Durum: EF Core, varsayılan olarak çekilen entity’leri ChangeTracker ile takip eder. Eğer veriyi sadece okumak istiyorsanız bu takip fazladan bellek ve CPU kullanabilir.

Kötü örnek:

// Kötü: sadece okuma ama tracking açık
var customers = await db.Customers.ToListAsync();

İyi örnek:

// İyi: okuma işlemlerinde AsNoTracking tercih edilebilir
var customers = await db.Customers
    .AsNoTracking() // takip devre dışı => daha az bellek/CPU
    .ToListAsync();

Not: AsNoTracking() SQL çıktısını değiştirmez — sorgu aynı SQL'i üretir. Fark, client-side davranıştadır (nesneler ChangeTracker'a eklenmez).

Örnek SQL (basit SELECT):

SELECT [c].[Id], [c].[Name], [c].[Email]
FROM [Customers] AS [c];

3) Büyük result set’leri bellekle çekmekten kaçınmak

Durum: Tüm tabloyu bir kerede .ToList() ile almak bellek tüketimini artırabilir; çok büyük tablolar için risk vardır.

Çözüm 1 — Sayfalama (paging):

int page = 1;
int pageSize = 1000;
var pageData = await db.Logs
    .OrderBy(l => l.Id) // sıralama, paging için gerekli
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .AsNoTracking()
    .ToListAsync();

Bu LINQ’in SQL karşılığı (SQL Server):

SELECT [l].*
FROM [Logs] AS [l]
ORDER BY [l].[Id]
OFFSET 0 ROWS FETCH NEXT 1000 ROWS ONLY;

Çözüm 2 — Streaming (büyük veriyi satır satır işlemek):

// EF Core 3+ ile AsAsyncEnumerable kullanarak stream edebilirsiniz
await foreach (var log in db.Logs.AsNoTracking().AsAsyncEnumerable())
{
    ProcessLog(log);
}

Stream edilen sorgu genelde standart bir SELECT olarak gider; ancak veriler işlem sırasında belleğe toplanmaz.

4) Include vs Select (projection) — gereksiz join'lerden kaçınmak

Durum: Include ilişkili tüm nesneleri getirir. Eğer sadece birkaç alan veya bir aggregate istiyorsanız Select genelde daha hafif olur.

Kötü örnek (gereksiz grafik çekme):

var customers = await db.Customers
    .Include(c => c.Orders) // bütün order nesnelerini getirir
    .ToListAsync();

Bu tip bir Include için oluşabilecek SQL (basit LEFT JOIN örneği):

SELECT [c].*, [o].*
FROM [Customers] AS [c]
LEFT JOIN [Orders] AS [o] ON [o].[CustomerId] = [c].[Id]

Eğer sadece order sayısı gerekiyorsa projection daha uygun:

var list = await db.Customers
    .Select(c => new {
        c.Id,
        c.Name,
        OrderCount = c.Orders.Count()
    })
    .AsNoTracking()
    .ToListAsync();

Bu, genelde correlated subquery veya GROUP BY kullanılarak şu SQL’e dönüşür:

SELECT [c].[Id], [c].[Name],
       (SELECT COUNT(*) FROM [Orders] AS [o] WHERE [o].[CustomerId] = [c].[Id]) AS [OrderCount]
FROM [Customers] AS [c];

Projection çoğu durumda daha az veri taşır ve client hafızasında daha az obje oluşturur.

5) Client-side evaluation — LINQ içinde C# fonksiyonları kullanırken dikkat

Durum: Where gibi bir filtrede C# tarafında bir metot kullanırsanız (EF bunu SQL’e çeviremezse) tüm tablo client’a çekilip filtre client-side uygulanır.

Kötü örnek:

bool IsGood(string s) => s.StartsWith("A");

var q = db.Customers.Where(c => IsGood(c.Name)).ToList(); // EF bu durumu SQL'e çeviremeyebilir

Bunun yerine mümkün olduğunca SQL çevirisi yapılabilen ifadeler kullanın:

var q = await db.Customers
    .Where(c => c.Name.StartsWith("A")) // SQL'e çevrilebilir
    .ToListAsync();

Bu durumda SQL örneği:

SELECT [c].*
FROM [Customers] AS [c]
WHERE [c].[Name] LIKE N'A%';

6) DbContext lifetime — genelde Scoped tercih edilir

Durum: DbContext uzun ömürlü (ör. singleton) tutulursa concurrency, bellek artışı veya beklenmeyen hatalar görülebilir. Genelde web uygulamalarında Scoped (her HTTP isteği için yeni) daha uygundur.

Öneri ifadesi (yumuşak):
 Genellikle, DbContext’i Scoped olarak kaydetmek uygulamalar için daha güvenli ve öngörülebilir davranış sağlar. Çok uzun süre açık tutulan context’ler beklenmeyen durumlara yol açabilir.

Program.cs örneği:

// Genellikle önerilen kullanım (ASP.NET Core)
services.AddDbContext<MyDbContext>(options =>
    options.UseSqlServer(connectionString));

7) Çok sık SaveChanges() çağırmak — batch yapmak daha verimli olur

Durum: Döngü içinde her öğe için SaveChanges() çağırmak her seferinde veritabanına gidilmesine neden olur; büyük işlemlerde maliyetlendirir.

Kötü örnek:

foreach (var item in items)
{
    db.Set<MyEntity>().Add(item);
    db.SaveChanges(); // her iterasyonda veritabanına gidiliyor
}

Daha verimli:

db.Set<MyEntity>().AddRange(items);
await db.SaveChangesAsync(); // tek seferde kaydet

Çok büyük hacimlerde SqlBulkCopy veya EFCore.BulkExtensions gibi araçlar değerlendirilebilir.

8) Transaction süreleri — kısa tutmak genelde daha iyi

Durum: Uzun süre açık kalan transaction’lar kilitlenmelere ve blocking’e yol açabilir. Mümkünse transaction’ı kısa tutun; uzun işlemleri transaction dışında yapılan adımlar olarak tasarlayın (ör. background job, saga pattern).

Örnek (kısa tutma):

using var tx = await db.Database.BeginTransactionAsync();
try
{
    // mümkün olduğunca hızlı işlemler
    await db.SaveChangesAsync();
    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();
    throw;
}

9) Asenkronu bloklayıcı çağrılarla karıştırmamak — await tercih edin

Durum: .Result veya .Wait() gibi blocking çağrılar threadpool'u meşgul edebilir; özellikle yüksek istek hacminde önerilmez. async/await zincirini korumaya çalışın.

Kötü örnek:

var customers = db.Customers.ToListAsync().Result; // blocking, tavsiye edilmez

İyi örnek:

var customers = await db.Customers.ToListAsync(); // non-blocking, önerilen yol

10) Compiled Queries — sık kullanılan karmaşık sorgularda fayda sağlayabilir

Durum: Çok sık çağrılan karmaşık LINQ sorgularının ifade ağacı derlenmesi maliyet yaratabilir. EF.CompileQuery ile çağrı maliyetini azaltabilirsiniz.

Örnek (EF Core):

// Derlenmiş sorgu örneği: sık kullanılan bir sorguda fayda sağlar
static readonly Func<MyDbContext, int, Task<Customer>> _getById =
    EF.CompileAsyncQuery((MyDbContext ctx, int id) =>
        ctx.Customers.Where(c => c.Id == id));

var customer = await _getById(db, 123);

SQL aynı olacaktır; ama sorgunun expression tree derlenmesi tekrar yapılmaz, bu da CPU kazancı sağlayabilir.

11) Ham SQL kullanırken parametreleme — injection riskine dikkat

Durum: Raw SQL ile çalışırken parametreleri interpolasyonla doğrudan eklemek riskli olabilir. Parametreli/Interpolated API’leri kullanmak daha güvenli.

Riskli örnek:

var sql = $"SELECT * FROM Customers WHERE Name = '{userInput}'";
var list = db.Customers.FromSqlRaw(sql).ToList(); // injection riski

Güvenli örnek:

var list = db.Customers.FromSqlInterpolated($"SELECT * FROM Customers WHERE Name = {userInput}").ToList();

12) Ölçme ve loglama — tahmin yerine veriyle gidin

Durum: Performansla ilgili değişiklik yapmadan önce ölçüm yapmak her zaman daha güvenli. EF SQL loglarını açıp slow query’leri tespit edin; APM, MiniProfiler veya basit Stopwatch ile hot-path’leri inceleyin.

EF Core logging örneği:

var loggerFactory = LoggerFactory.Create(builder =>
{
    builder.AddConsole();
});

optionsBuilder
    .UseLoggerFactory(loggerFactory)
    .EnableSensitiveDataLogging(); // production'da hassas veri loglanmasına dikkat

Final, kısa kontrol listesi:

  • Okuma endpoint’lerinde AsNoTracking() genellikle faydalıdır.
  • Döngüler içinde ayrı DB çağrısı olup olmadığına bakın; varsa tek sorguda çözmeyi düşünün.
  • Büyük listelerde sayfalama veya streaming uygulamak belleği rahatlatır.
  • DbContext genelde Scoped olarak kullanılması uygulama davranışını öngörülebilir kılar.
  • Çok sayıda küçük SaveChanges() yerine batch işlemler performans sağlar.
  • Sorguları loglayıp, gerçek SQL’i incelemek ve index planını kontrol etmek en etkili yöntemlerden biridir.
