Dependency Injection Her Sorunu Çözmez: .NET’te Doğru Kullanım Rehberi

dependency-injection·2 Nisan 2026·~4 dk okuma

Dependency Injection (DI) modern .NET uygulamalarının temel taşlarından biri. Doğru kullanıldığında kodu esnek, test edilebilir ve yönetilebilir hale getirir. Ama burada kritik bir gerçek var:
 DI her sorunu çözmez. Hatta yanlış kullanıldığında işleri daha karmaşık hale getirir.

Bu yazıda DI’ın ne olduğunu kısaca netleştirip, en sık yapılan hataları ve doğru kullanım yaklaşımını gerçek senaryolar üzerinden anlatacağız.

Dependency Injection nedir?

Dependency Injection, bir sınıfın ihtiyaç duyduğu bağımlılıkların (dependency) dışarıdan verilmesidir.

Basitçe:

Bir sınıf, ihtiyacı olan nesneyi kendi oluşturmaz; dışarıdan alır.

Neden önemli?

  • Bağımlılıkları azaltır (loosely coupled yapı)
  • Test yazmayı kolaylaştırır
  • Kodun değişime dayanıklılığını artırır

Temel örnek

Yanlış yaklaşım (bağımlılık içeride oluşturuluyor):

public class OrderService
{
    private readonly EmailService _emailService;

    public OrderService()
    {
        _emailService = new EmailService(); // Bağımlılık burada oluşturuluyor (sıkı bağlılık)
    }

    public void CreateOrder()
    {
        // Sipariş işlemleri...
        _emailService.Send(); // EmailService'e doğrudan bağlı
    }
}

Sorun:

  • EmailService değişirse OrderService de değişmek zorunda
  • Test yazmak zorlaşır

Doğru yaklaşım (Dependency Injection):

public class OrderService
{
    private readonly IEmailService _emailService;

    public OrderService(IEmailService emailService)
    {
        _emailService = emailService; // Bağımlılık dışarıdan veriliyor
    }

    public void CreateOrder()
    {
        _emailService.Send(); // Hangi implementasyon olduğu önemli değil
    }
}

Burada:

  • IEmailService bir interface (soyutlama)
  • Gerçek implementasyon dışarıdan gelir

DI Container nedir?

.NET’te DI işlemini yöneten yapıya DI Container denir.

Bu yapı:

  • Hangi interface hangi class’a karşılık geliyor bilir
  • Nesneleri oluşturur
  • Lifecycle (ömür) yönetimini yapar

Kayıt örneği

builder.Services.AddScoped<IEmailService, EmailService>(); 
// IEmailService istendiğinde EmailService verilir

Lifetime nedir?

DI kullanırken en kritik konulardan biri lifetime’dır.
Yani bir nesnenin ne kadar süre yaşadığı.

1. Transient

services.AddTransient<IMyService, MyService>();
  • Her istekte yeni instance oluşturulur

2. Scoped

services.AddScoped<IMyService, MyService>();
  • Her HTTP request için 1 instance

3. Singleton

services.AddSingleton<IMyService, MyService>();
  • Uygulama boyunca tek instance

Yanlış lifetime seçimi ciddi bug’lara yol açar.

En sık yapılan hatalar

1) Her şeyi DI ile çözmeye çalışmak

DI bir araçtır, mimari değildir.

Yanlış yaklaşım:

  • Her class için interface yazmak
  • Basit sınıfları bile DI’a sokmak
public interface IStringHelper
{
    string ToUpper(string input);
}

Bu gereksizdir.

Kural: Gerçek bir değişim ihtiyacı yoksa soyutlama yapma

2) Over-engineering (gereksiz karmaşıklık)

DI kullanayım derken sistem şuna döner:

Controller → Service → Manager → Handler → Provider → Helper

Her katman:

  • interface
  • implementasyon
  • DI kaydı

Sonuç:

  • Okunması zor
  • Debug zor
  • Gereksiz karmaşıklık

Basit çözümler çoğu zaman daha iyidir.

3) Service Locator kullanmak

Service Locator şu demektir:

public class OrderService
{
    private readonly IServiceProvider _serviceProvider;

    public OrderService(IServiceProvider serviceProvider)
    {
        _serviceProvider = serviceProvider;
    }

    public void CreateOrder()
    {
        var emailService = _serviceProvider.GetService<IEmailService>();
        emailService.Send();
    }
}

Sorun:

  • Bağımlılıklar gizlenir
  • Class neye bağlı belli olmaz
  • Test etmek zorlaşır

Doğru yöntem: Constructor Injection kullanmak

4) Yanlış lifetime kullanımı

En tehlikeli hatalardan biri.

Hatalı kullanım:

services.AddSingleton<MyService>();
services.AddScoped<DbContext>();

Eğer Singleton bir servis, Scoped bir servisi kullanıyorsa: Runtime hatası veya beklenmeyen davranış oluşur.

Çünkü:

  • Singleton tek instance
  • Scoped request bazlı

Kural:
 Uzun ömürlü servis, kısa ömürlü servise bağımlı olmamalı.

5) DI’ı test için kullanmamak

DI’ın en büyük avantajı testtir.

public class FakeEmailService : IEmailService
{
    public void Send()
    {
        // Gerçek mail göndermez
    }
}

Testte:

var service = new OrderService(new FakeEmailService());
// Test sırasında gerçek servis yerine fake kullanılır

Eğer testte DI kullanmıyorsan, DI’ın yarısını kullanıyorsun demektir.

Doğru kullanım yaklaşımı

DI’ı doğru kullanmak için şu prensipleri benimse:

1. Sadece ihtiyaç varsa soyutla

Her class için interface yazma

2. Constructor Injection kullan

Bağımlılıkları açıkça göster

3. Lifetime’ı bilinçli seç

  • Stateless → Transient
  • Request bazlı → Scoped
  • Global → Singleton

4. Basit kal

Karmaşık yapı = zor bakım

5. Test yaz

DI’ın asıl gücü burada

Ne zaman DI kullanmamalısın?

Bazı durumlarda DI gereksizdir:

  • Utility class’lar (string helper gibi)
  • Stateless ve basit fonksiyonlar
  • Tek kullanımlık sınıflar

Her şeyi DI’a sokmak iyi pratik değildir.

Sonuç

Dependency Injection güçlü bir araçtır. Ama doğru kullanılmadığında:

  • Gereksiz soyutlama
  • Karmaşık yapı
  • Debug zorluğu
  • Performans sorunları

gibi problemler üretir.

Asıl mesele DI kullanmak değil, ne zaman kullanmamayı bilmektir.

İyi bir .NET geliştiricisi:

  • DI’ı bilinçli kullanır
  • Gereksiz abstraction’dan kaçınır
  • Lifetime’ı doğru yönetir
  • Kodunu sade tutar

Çünkü yazılımda kalite, kullanılan araçlardan değil, o araçların nasıl kullanıldığından gelir.
