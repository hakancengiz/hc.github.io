.NET Core’da Middleware Akışı: İstek Sisteme Nasıl Girer, Nasıl Çıkar?

yazılım·28 Mart 2026·~5 dk okuma

Web uygulamalarında en çok kafa karıştıran konulardan biri, isteğin uygulamaya girdikten sonra hangi sırayla işlendiğidir. Özellikle .NET Core tarafında middleware kavramını tam anlamadan ilerlemek, hem hata ayıklamayı zorlaştırır hem de performans ve güvenlik açısından yanlış kararlar vermeye neden olur.

Bu yazıda middleware’in ne olduğunu, isteğin uygulamaya nasıl girdiğini, neden bazı middleware’lerin üstte bazıların altta yer aldığını ve akışın nasıl çalıştığını adım adım anlatacağız.

Middleware nedir?

Middleware, HTTP isteği ile HTTP yanıtı arasında çalışan aracı bileşendir.

Daha sade söyleyelim: Uygulamaya gelen her istek, tek bir yerde değil; bir dizi middleware üzerinden geçer. Bu bileşenler isteği inceleyebilir, değiştirebilir, kısa yoldan cevap dönebilir ya da bir sonraki adıma iletebilir.

Middleware’i bir güvenlik kapısı, bir kontrol noktası veya bir işlem hattı gibi düşünebilirsiniz.

Örneğin:

  • kimlik doğrulama burada yapılabilir
  • loglama burada yapılabilir
  • hata yakalama burada yapılabilir
  • statik dosya sunumu burada yapılabilir

İstek akışı nasıl ilerler?

Bir HTTP isteği uygulamaya geldiğinde genellikle şu mantıkla ilerler:

  1. İstek uygulamaya ulaşır
  2. Middleware zincirinin en üstünden başlar
  3. Her middleware kendi işini yapar
  4. İsterse isteği bir sonraki middleware’e gönderir
  5. En sonunda endpoint’e (controller / minimal API) ulaşır
  6. Cevap geri dönerken zincir ters yönde çalışır

Kritik nokta:
Request yukarıdan aşağı iner, response aşağıdan yukarı çıkar.

Pipeline mantığı

Pipeline = boru hattı demektir.

.NET Core’da middleware’ler bir zincir halinde çalışır. Her middleware’in elinde bir sonraki adıma geçmek için bir fonksiyon vardır: next()

Middleware iki şey yapabilir:

  • Akışı devam ettirmek (next() çağırır)
  • Akışı kesmek (next() çağırmaz)

Eğer next() çağrılmazsa, alttaki middleware’ler hiç çalışmaz

Basit bir örnek

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    // İstek ilk geldiğinde burası çalışır
    Console.WriteLine("1. Middleware - İstek geldi");

    // Sonraki middleware'e geç
    await next();

    // Response geri dönerken burası çalışır
    Console.WriteLine("1. Middleware - Cevap dönüyor");
});

app.Use(async (context, next) =>
{
    // İkinci middleware çalışır
    Console.WriteLine("2. Middleware - İşlem başladı");

    await next();

    // Response dönerken tekrar buraya girer
    Console.WriteLine("2. Middleware - İşlem bitti");
});

app.MapGet("/", () => "Merhaba dünya");

app.Run();

Çalışma sırası:

1. Middleware — İstek geldi

2. Middleware — İşlem başladı

Endpoint çalışır

2. Middleware — İşlem bitti

1. Middleware — Cevap dönüyor

İşte middleware mantığı bu kadar net.

Use, Run, Map farkı

Use

Zincire katılır, isterse devam eder

app.Use(async (context, next) =>
{
    await next(); // zinciri devam ettirir
});

Run

Zinciri keser

app.Run(async context =>
{
    // Buradan sonra başka middleware çalışmaz
    await context.Response.WriteAsync("Bitti");
});

Map

Yola göre dallanma yapar

app.Map("/admin", adminApp =>
{
    adminApp.Run(async context =>
    {
        await context.Response.WriteAsync("Admin alanı");
    });
});

Middleware sırası neden kritik?

Çünkü davranışı direkt değiştirir.

Örnek:

  • Authentication → önce çalışmalı
  • Authorization → sonra çalışmalı

Yanlış sıralarsan sistem doğru çalışmaz.

Genel kural:

  • Hata yakalama → en üst
  • Güvenlik → ortada
  • Endpoint → en altta

Tipik middleware sıralaması

app.UseExceptionHandler("/error"); // Hataları yakalar

app.UseHttpsRedirection(); // HTTP → HTTPS

app.UseStaticFiles(); // Statik dosyalar

app.UseRouting(); // Routing başlar

app.UseAuthentication(); // Kimlik doğrulama

app.UseAuthorization(); // Yetki kontrolü

app.MapControllers(); // Endpoint

Custom middleware yazımı

public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;

    public RequestTimingMiddleware(RequestDelegate next)
    {
        // Bir sonraki middleware
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // Başlangıç zamanı
        var start = DateTime.UtcNow;

        // Sonraki middleware'e geç
        await _next(context);

        // Süre hesapla
        var duration = DateTime.UtcNow - start;

        Console.WriteLine($"Süre: {duration.TotalMilliseconds} ms");
    }
}

Kullanımı:

app.UseMiddleware<RequestTimingMiddleware>();

RequestDelegate = “bir sonraki middleware”

Gerçekten ne yapıyoruz?

Aslında yaptığımız şey çok basit:

Pipeline’a kendi kontrol noktanı ekliyorsun.

Yani diyorsun ki:

“Her istek geldiğinde önce buradan geçsin, ben bir şey yapayım, sonra devam etsin.”

Kodun mantığını parçalayalım

1. RequestDelegate _next ne?

Bu en kritik nokta. _next dediğimiz şey: “bir sonraki middleware’i çağıran fonksiyon”. Yani, senin middleware’inden sonra kim varsa, ona geçiş kapısı bu.

Şöyle düşün: Middleware1 → Middleware2 → Middleware3

Sen Middleware2’sin. _next dediğin şey: Middleware3’e geçiş bileti.

2. Constructor (kurucu metot) neden var?

public RequestTimingMiddleware(RequestDelegate next)
{
    _next = next;
}

Burada framework sana otomatik olarak “bir sonraki adımı” veriyor.

Sen de: “Tamam bunu saklıyorum, birazdan kullanacağım” diyorsun.

3. InvokeAsync neden var?

public async Task InvokeAsync(HttpContext context)

Bu metod: Her HTTP isteğinde çalışan yer

Yani:

  • 1 istek → 1 kez çalışır
  • 1000 istek → 1000 kez çalışır

4. Akışın asıl büyüsü burada

var startTime = DateTime.UtcNow;

await _next(context);

var duration = DateTime.UtcNow - startTime;

Bunu iyi anlamazsan middleware’i yarım öğrenmiş olursun.

Adım adım:

await _next(context) öncesi:

  • İstek daha aşağı gitmedi
  • Sen request tarafındasın

Burada:

  • log alabilirsin
  • header okuyabilirsin
  • validation yapabilirsin

await _next(context):

  • İstek diğer middleware’lere gider
  • en sonunda endpoint çalışır

await _next(context) sonrası:

(Artık response geri dönüyor)

  • response’u değiştirebilirsin
  • süre hesaplayabilirsin
  • log yazabilirsin

Bu middleware özelinde ne yaptık?

Bu örnek middleware’in amacı: İsteğin ne kadar sürdüğünü ölçmek

Adım adım:

  1. İstek geldi → zamanı kaydet (startTime)
  2. _next ile sistemi çalıştır (diğer middleware + endpoint)
  3. İş bittikten sonra tekrar zaman al
  4. Aradaki farkı hesapla
  5. Logla

Neden önemli?

Bu yapı sayesinde:

  • Performans ölçersin
  • Yavaş endpoint’leri yakalarsın
  • Gerçek kullanıcı deneyimini görürsün

Production’da bu tarz middleware’ler: APM (Application Performance Monitoring) sistemlerinin temelidir.

Kısa ve net özet

Custom middleware yazmak = “Her isteğin geçeceği bir kontrol noktası koymak”

Ve en kritik olay:

_next çağırırsan akış devam eder.
 çağırmazsan sistemi burada durdurursun.

Akışı erken kesmek

app.Use(async (context, next) =>
{
    bool maintenance = false;

    if (maintenance)
    {
        // Zincir burada biter
        context.Response.StatusCode = 503;
        await context.Response.WriteAsync("Bakımda");
        return;
    }

    await next();
});

En kritik kafa karışıklığı

await next() öncesi = request
await next() sonrası = response

Bunu anlarsan middleware’i çözmüşsün demektir.

Hata yakalama neden en üstte?

Çünkü her şeyi kapsaması gerekir.

app.Use(async (context, next) =>
{
    try
    {
        await next();
    }
    catch (Exception ex)
    {
        Console.WriteLine(ex.Message);

        context.Response.StatusCode = 500;
        await context.Response.WriteAsync("Hata oluştu");
    }
});

Middleware vs Filter

Middleware:

  • Tüm pipeline
  • Global
  • Altyapı

Filter:

  • Controller seviyesinde
  • Daha spesifik
  • İş mantığına yakın

Nerede kullanılmalı?

Uygun:

  • logging
  • exception handling
  • auth
  • rate limiting

Uygun değil:

  • business logic
  • DTO validation
  • action bazlı kararlar

Sık yapılan hatalar

  1. next() çağırmamak
  2. Yanlış sıralama
  3. Gereksiz ağır işlem
  4. Response başladıktan sonra header değiştirmek
  5. Her şeyi middleware yapmak

Sonuç

Middleware mantığını şöyle özetle:

  • İstek girer
  • Zincirden geçer
  • next() varsa devam eder
  • Response geri döner
  • Kodlar ters yönde tekrar çalışır

Bu modeli kafana oturttuğun anda:

  • debug kolaylaşır
  • performans artar
  • mimari temizleşir
