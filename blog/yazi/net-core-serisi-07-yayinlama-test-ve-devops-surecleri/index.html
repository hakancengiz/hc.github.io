Kod yazmak kadar onu yayınlamak, test etmek ve sürekli güncel tutmak da önemlidir.
Modern yazılım geliştirme süreci, yalnızca “build” değil, aynı zamanda:

  • Test (Doğrulama)
  • Publish (Dağıtım)
  • DevOps (Sürekli Entegrasyon & Dağıtım)
     adımlarını içerir.

1. Publish (Yayınlama) Süreci

.NET Core, platformdan bağımsız çalışabildiği için iki farklı yayın türü sunar:

| Tür                     | Açıklama                       | Boyut | Gereksinim           |
| ----------------------- | ------------------------------ | ----- | -------------------- |
| **Framework-Dependent** | .NET yüklü makinelerde çalışır | Küçük | .NET Runtime gerekir |
| **Self-Contained**      | Her şeyi içinde barındırır     | Büyük | .NET gerekmez        |

Publish Örneği

# Framework dependent publish
dotnet publish -c Release -o ./publish

# Self-contained publish (örnek: Windows 64-bit)
dotnet publish -c Release -r win-x64 --self-contained true

Açıklama:

  • -c Release → derleme modu
  • -r win-x64 → hedef işletim sistemi
  • --self-contained → tüm bağımlılıkları içerir

Çıktı klasörü:

publish/
 ┣ MyApp.dll
 ┣ appsettings.json
 ┗ MyApp.deps.json

2. appsettings ve Ortam (Environment) Yönetimi

Yayın ortamlarında (örneğin test, staging, production) farklı ayarlar gerekebilir.
.NET Core, bu işi Environment sistemiyle otomatikleştirir.

appsettings.json dosyaları:

appsettings.json → Ortak ayarlar 
appsettings.Development.json → Geliştirme ortamı 
appsettings.Production.json → Yayın ortamı

Örnek:

// appsettings.Production.json
{
  "Logging": {
    "LogLevel": {
      "Default": "Warning"
    }
  },
  "ConnectionStrings": {
    "DefaultConnection": "Server=prod-db;Database=MyApp;User Id=sa;Password=SecurePass;"
  }
}

Uygulama çalışırken ortam belirlenir:

set ASPNETCORE_ENVIRONMENT=Production

Not:

  • Yerel ortamda Development varsayılan olarak gelir.
  • Yayın ortamında Production olmalıdır.

3. Unit Test (Birim Testi)

Test yazmak, kodun doğruluğunu ve sürdürülebilirliğini sağlar.
.NET Core’da test projeleri için xUnit, NUnit veya MSTest sıkça kullanılır.

Örnek:

// Tests/UserServiceTests.cs
// UserService'in davranışını test eden birim testi
public class UserServiceTests
{
    private readonly Mock<IUserRepository> _mockRepo;
    private readonly UserService _service;

    public UserServiceTests()
    {
        // 1️⃣ Mock repository oluşturulur
        _mockRepo = new Mock<IUserRepository>();

        // 2️⃣ Test verisi hazırlanır
        var users = new List<User>
        {
            new User { Id = 1, Name = "Hakan", Email = "hakan@mail.com" },
            new User { Id = 2, Name = "Ahmet", Email = "" }
        };

        // 3️⃣ Repository davranışı tanımlanır
        _mockRepo.Setup(r => r.GetAllAsync()).ReturnsAsync(users);

        // 4️⃣ Servis mock repository ile oluşturulur
        _service = new UserService(_mockRepo.Object);
    }

    [Fact]
    public async Task GetActiveUsersAsync_ShouldReturn_OnlyUsersWithEmail()
    {
        // 5️⃣ Servis çağrılır
        var result = await _service.GetActiveUsersAsync();

        // 6️⃣ Doğrulama yapılır
        Assert.Single(result); // sadece 1 kullanıcı e-postalı
        Assert.Equal("Hakan", result.First().Name);
    }
}

Açıklama:

  • Mock nesneleri, bağımlılıkları taklit eder (veritabanına bağlanmaz).
  • Testler “iş mantığının doğru çalıştığını” garantiler.

4. Integration Test (Entegrasyon Testi)

Birim testin aksine, sistemin tüm parçalarını birlikte test eder.

// Tests/UserControllerTests.cs
public class UserControllerTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public UserControllerTests(WebApplicationFactory<Program> factory)
    {
        // 1️⃣ Gerçek API host'u ayağa kaldırılır
        _client = factory.CreateClient();
    }

    [Fact]
    public async Task GetUsers_ShouldReturn_OK()
    {
        // 2️⃣ /api/user isteği gönderilir
        var response = await _client.GetAsync("/api/user");

        // 3️⃣ Yanıt doğrulanır
        response.EnsureSuccessStatusCode();
        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
    }
}

5. Postman / Swagger ile Manuel Test

Postman

  • API endpoint’lerini manuel test etmeni sağlar.
  • Header, body, token, JSON payload gibi parametreleri kolayca ayarlayabilirsin.

Swagger

.NET Core API projelerinde varsayılan olarak gelir.

// Program.cs
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

app.UseSwagger();
app.UseSwaggerUI();

Artık tarayıcıda şu adrese giderek API’yi test edebilirsin:

https://localhost:5001/swagger

6. CI/CD (Continuous Integration & Deployment)

Amaç: Her kod değişikliğinde otomatik test, derleme ve dağıtım yapmak.

Örnek: GitHub Actions Pipeline (YAML)

# .github/workflows/dotnet.yml
name: Build & Deploy .NET Core API

on:
  push:
    branches: [ "main" ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      # 1️⃣ Kodu çek
      - name: Checkout
        uses: actions/checkout@v3

      # 2️⃣ .NET kurulumu
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: '8.0.x'

      # 3️⃣ Bağımlılıkları indir
      - name: Restore dependencies
        run: dotnet restore

      # 4️⃣ Build işlemi
      - name: Build
        run: dotnet build --no-restore -c Release

      # 5️⃣ Test çalıştır
      - name: Run Tests
        run: dotnet test --no-build --verbosity normal

      # 6️⃣ Yayınlama
      - name: Publish
        run: dotnet publish -c Release -o ./publish

Açıklama:
Bu işlem “main” branch’e yapılan her push sonrası çalışır.
Kod test edilir, build edilir, ardından “publish” klasörüne alınır.

7. Azure DevOps Pipeline Örneği

Azure DevOps’ta YAML yapısı benzerdir:

trigger:
- main

pool:
  vmImage: 'windows-latest'

steps:
- task: DotNetCoreCLI@2
  inputs:
    command: 'restore'
    projects: '**/*.csproj'

- task: DotNetCoreCLI@2
  inputs:
    command: 'build'
    projects: '**/*.csproj'
    arguments: '--configuration Release'

- task: DotNetCoreCLI@2
  inputs:
    command: 'publish'
    projects: '**/*.csproj'
    arguments: '--configuration Release --output $(Build.ArtifactStagingDirectory)'

8. Deployment (Yayına Alma)

Yayınlanan klasör (publish/) bir sunucuya veya buluta yüklenir.
 Örneğin IIS, Docker veya Azure App Service kullanılabilir.

IIS Dağıtımı:

  1. Publish klasörünü sunucuya kopyala
  2. IIS’te yeni bir Application Pool oluştur
  3. .NET Core Hosting Bundle kurulu olduğundan emin ol
  4. Uygulamanın web.config dosyası otomatik olarak ayarlanır

9. Docker ile Yayınlama

# Dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet restore
RUN dotnet publish -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]

Oluştur ve çalıştır:

docker build -t myapp .
docker run -p 8080:8080 myapp

Avantaj:

  • Taşınabilirlik (her ortamda aynı çalışır)
  • Kolay otomasyon (CI/CD pipeline’larına dahil edilebilir)

10. Ortam Değişkenleri (Environment Variables)

Yayın ortamında gizli bilgileri (şifre, bağlantı dizeleri, API key vb.)
appsettings.json yerine environment değişkenlerinde tutmak güvenlidir.

Örnek:

# Linux ortamında
export ConnectionStrings__DefaultConnection="Server=db;Database=myapp;User=sa;Password=12345;"

Program.cs’de erişim:

var connection = builder.Configuration.GetConnectionString("DefaultConnection");

Özet:

| Aşama                      | Açıklama                                   |
| -------------------------- | ------------------------------------------ |
| **Publish**                | Uygulamanın dağıtıma hazırlanması          |
| **Test**                   | Birim ve entegrasyon testleriyle doğrulama |
| **Swagger / Postman**      | Manuel test araçları                       |
| **CI/CD**                  | Otomatik build ve test sistemleri          |
| **Deployment**             | IIS / Docker / Azure App Service           |
| **Environment Management** | Ortama göre yapılandırma ayarları          |
