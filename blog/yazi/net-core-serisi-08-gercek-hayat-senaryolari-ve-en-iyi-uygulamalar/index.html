Artık .NET Core mimarisini, katmanlı yapıyı, güvenliği, testleri ve dağıtımı öğrendik.
 Bu noktada mesele “nasıl çalışıyor”dan çok “gerçekte nasıl yönetilir” haline gelir.

Bu yazıda:

  • Gerçek dünyada kullanılan mimari desenleri,
  • Performans ve bakım odaklı ipuçlarını,
  • Ve ekip içi standartlaşmayı ele alacağız.

1. Gerçek Hayat Proje Yapısı

Profesyonel bir .NET Core projesi genellikle şu şekilde yapılandırılır;

MyCompany.MyProject
 ┣ MyProject.API → Controller’lar, DTO, Middleware
 ┣ MyProject.Application → Business logic (Service, Interface)
 ┣ MyProject.Domain → Entity, DTO, Validation
 ┣ MyProject.Infrastructure → EF Core, Repository, Logging, Email
 ┗ MyProject.Tests → Unit & Integration Tests

Not:

  • “Application” katmanı business mantığını taşır.
  • “Infrastructure” katmanı teknik detayları (ör. EF Core, Mail, Redis) kapsar.
  • “Domain” saf C# kodları içerir, dış bağımlılığı yoktur.

Bu yapı, Clean Architecture veya Onion Architecture olarak da bilinir.

2. Clean Architecture Mantığı

Clean Architecture’ın temel ilkesi şudur:

“Bağımlılıklar dıştan içe doğru akabilir ama asla tersine değil.”

Yani:

  • API → Application → Domain
  • Ancak Domain, hiçbir zaman API’ye veya Infrastructure’a bağımlı olamaz.

Bu sayede:

  • Test yazmak kolaylaşır,
  • Değişiklikler yalnızca ilgili katmanı etkiler,
  • Kod tekrar kullanılabilir hale gelir.

3. Katmanlar Arası Veri Akışı (Gerçek Senaryo)

Gerçek bir senaryo:

Kullanıcı yeni bir sipariş oluşturur ve sistem hem veritabanına kaydeder hem de e-posta gönderir.
// API/Controllers/OrderController.cs
[ApiController]
[Route("api/[controller]")]
public class OrderController : ControllerBase
{
    private readonly IOrderService _orderService;

    public OrderController(IOrderService orderService)
    {
        _orderService = orderService;
    }

    // Yeni sipariş oluşturma endpoint'i
    [HttpPost]
    public async Task<IActionResult> CreateOrder(CreateOrderDto orderDto)
    {
        // 1️⃣ Servis katmanına sipariş verisini gönder
        var result = await _orderService.CreateOrderAsync(orderDto);

        // 2️⃣ Sonuç başarısızsa 400 döner
        if (!result.Success)
            return BadRequest(result.Message);

        // 3️⃣ Başarılıysa 201 Created döner
        return CreatedAtAction(nameof(GetOrderById), new { id = result.OrderId }, result);
    }

    [HttpGet("{id}")]
    public async Task<IActionResult> GetOrderById(int id)
    {
        var order = await _orderService.GetOrderByIdAsync(id);
        return order != null ? Ok(order) : NotFound();
    }
}

İş Mantığı (Service Katmanı)

// Application/Services/OrderService.cs
public class OrderService : IOrderService
{
    private readonly IOrderRepository _orderRepository;
    private readonly IEmailService _emailService;

    public OrderService(IOrderRepository orderRepository, IEmailService emailService)
    {
        _orderRepository = orderRepository;
        _emailService = emailService;
    }

    public async Task<ServiceResult> CreateOrderAsync(CreateOrderDto dto)
    {
        try
        {
            // 1️⃣ DTO → Entity dönüşümü
            var order = new Order
            {
                CustomerId = dto.CustomerId,
                Total = dto.Total,
                CreatedAt = DateTime.Now
            };

            // 2️⃣ Veritabanına kayıt
            await _orderRepository.AddAsync(order);

            // 3️⃣ E-posta bildirimi gönderimi
            await _emailService.SendAsync(dto.CustomerEmail, "Sipariş alındı", "Siparişiniz başarıyla oluşturuldu.");

            // 4️⃣ Başarı mesajı döndür
            return new ServiceResult(true, "Sipariş başarıyla oluşturuldu.", order.Id);
        }
        catch (Exception ex)
        {
            // Hata loglanır
            Console.WriteLine($"[ERROR] {ex.Message}");
            return new ServiceResult(false, "Sipariş oluşturulamadı.");
        }
    }
}

4. DTO, Entity ve Result Nesneleri

Gerçek projelerde servis sonuçlarını sadece bool döndürmek yerine
standardize edilmiş response modelleri kullanılır.

// Domain/Models/ServiceResult.cs
public class ServiceResult
{
    public bool Success { get; set; }
    public string Message { get; set; } = string.Empty;
    public int? OrderId { get; set; }

    public ServiceResult(bool success, string message, int? orderId = null)
    {
        Success = success;
        Message = message;
        OrderId = orderId;
    }
}

Böylece tüm API yanıtları aynı yapıda döner:

{
  "success": true,
  "message": "Sipariş başarıyla oluşturuldu.",
  "orderId": 12
}

5. Exception Handling (Gerçek Projede)

Gerçek projelerde hata yönetimi sadece try-catch ile değil,
 global middleware üzerinden yapılır.

// Middleware/ErrorHandlingMiddleware.cs
public class ErrorHandlingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ErrorHandlingMiddleware> _logger;

    public ErrorHandlingMiddleware(RequestDelegate next, ILogger<ErrorHandlingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context); // Sonraki middleware'e geç
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Beklenmeyen hata oluştu!");
            context.Response.StatusCode = 500;
            await context.Response.WriteAsJsonAsync(new
            {
                success = false,
                message = "Sunucu hatası, lütfen tekrar deneyin."
            });
        }
    }
}

Kaydet:

// Program.cs
app.UseMiddleware<ErrorHandlingMiddleware>();

6. Logging ve Monitoring (Gerçek Uygulamalarda)

Gerçek uygulamalarda loglar sadece konsola yazılmaz.
 Serilog, Seq, Elastic Stack (ELK) veya Application Insights gibi sistemlerle entegre edilir.

Serilog Kurulumu:

// Program.cs
Log.Logger = new LoggerConfiguration()
    .WriteTo.Console()
    .WriteTo.File("logs/app-.log", rollingInterval: RollingInterval.Day)
    .CreateLogger();

builder.Host.UseSerilog();

Böylece günlük log dosyaları otomatik döner:

logs/
 ┣ app-2025-10-17.log
 ┣ app-2025-10-18.log

7. Performans Optimizasyonu (Gerçek Senaryolar)

Gerçek sistemlerde performansın büyük kısmı:

  • Gereksiz veritabanı çağrılarından,
  • Yanlış lifetime kullanımından,
  • Eksik cache yönetiminden kaybedilir.

Örnek:

// Gereksiz sorgu
var allOrders = _context.Orders.ToList();

// Daha verimli yaklaşım
var lastOrders = _context.Orders
    .Where(o => o.CreatedAt > DateTime.Today.AddDays(-7))
    .AsNoTracking()
    .ToList();

Öneriler:

AsNoTracking() kullan
Gereksiz .Include() çağrılarından kaçın
Gerektiğinde MemoryCache veya Redis kullan
ILogger ile performans logları tut

8. Ekip Standardizasyonu

Gerçek hayatta kod kalitesini korumanın en etkili yolu: kuralların standartlaşmasıdır.

Öneriler:

  • Kodlama standartlarını (naming, indentation, yorum) belirle
  • Git branching modeli kullan (main, develop, feature/*)
  • Code review süreçlerini zorunlu tut
  • CI/CD pipeline’ına dotnet test dahil et
  • Pull request’lerde otomatik test sonucu kontrolü

9. Production İçin En İyi Uygulamalar

| Konu                  | En İyi Uygulama                   |
| --------------------- | --------------------------------- |
| **Bağlantı Dizeleri** | Environment variable’da sakla     |
| **Loglar**            | Dosya + merkezi sistem (ELK, Seq) |
| **Cache**             | Redis veya MemoryCache            |
| **Hata Yönetimi**     | Global middleware kullan          |
| **Config Yönetimi**   | appsettings.{env}.json kullan     |
| **Security**          | HTTPS, JWT, Rate Limiting         |
| **Veritabanı**        | Migration’ları CI/CD’de çalıştır  |
