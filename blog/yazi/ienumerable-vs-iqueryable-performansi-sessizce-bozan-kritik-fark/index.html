IEnumerable vs IQueryable — Performansı Sessizce Bozan Kritik Fark

csharp·15 Mart 2026·~5 dk okuma

Neden önemli?

Çoğu geliştirici IEnumerable ile IQueryable arasındaki farkı görmezden gelir; fakat fark, sorgunun nerede çalıştığını (memory mi yoksa database mi) belirler. Yanlış yerde filtre uygulamak, büyük veritabanı tablolarını istemeden client tarafına çekmene ve performans felaketine yol açar.

Temel kavramlar

  • IEnumerable<T>: Veriyi bellekte (in-memory) işler. LINQ to Objects burada çalışır. Sorguların çoğu C# kodu tarafından işletilir.
  • IQueryable<T>: Sorguyu temsil eden bir ifade ağacıdır (expression tree). Provider (ör. Entity Framework Core) bu ağacı alır ve SQL gibi hedef dile çevirir. Yani sorgu veritabanında çalışabilir.
  • Deferred execution (ertelenmiş yürütme): Where, Select gibi operasyonlar genelde hemen çalışmaz; yalnızca ToList(), ToArray(), First() gibi "materialize" eden çağrılarda gerçek yürütme başlar.
  • Expression Tree (İfade Ağacı): IQueryable sorgusunu temsil eden ağaçtır; EF Core bu ağacı parse edip SQL'e çevirir.

Basit örnek: LINQ to Objects (IEnumerable)

// Örnek veri: bellekte bir liste
var users = new List<User>
{
    new User { Id = 1, Name = "Ayşe", Age = 25 },
    new User { Id = 2, Name = "Mehmet", Age = 30 },
    // ...
};

// IEnumerable üzerinde Where ve Select çalışır — tüm liste bellekte
var adults = users
    .Where(u => u.Age >= 18) // → LINQ to Objects: C# kodu ile filtrelenir
    .Select(u => u.Name)     // → yine C# tarafında projection yapılır
    .ToList();               // → buraya kadar çalıştırma (materialize) gerçekleşir

// Açıklama: users zaten bellekte olduğu için sorgu doğrudan uygulama tarafından işletilir.

Basit örnek: EF Core ile IQueryable (veritabanında çalıştırılabilir)

// _context bir EF Core DbContext örneği varsayalım
IQueryable<User> query = _context.Users; // DbSet<User> IQueryable döner

// Bu sorgu henüz DB'ye gitmez — expression tree oluşturulur
var adultsQuery = query
    .Where(u => u.Age >= 18)   // Expression tree'ine Where eklenir
    .Select(u => new { u.Name, u.Age }); // projection da ifade ağacına eklenir

// Gerçek SQL yürütme ancak aşağıdaki çağrıda olur:
var results = await adultsQuery.ToListAsync(); // → EF Core SQL üretip DB'ye gönderir

// Açıklama: filtre ve projection DB tarafında çalıştığından sadece gerekli satırlar/kolonlar çekilir.

Kritik performans tuzağı: ToList()’i erken çağırma

// KÖTÜ: önce ToList() ile tüm veriyi çekiyoruz, sonra filtre uyguluyoruz — client-side filter
var bad = _context.Users
    .ToList()                   // → tüm Users tablosu belleğe çekilir (kötü)
    .Where(u => u.Age >= 18)    // → filtre client tarafında yapılır
    .ToList();                  // → gereksiz bellek ve network trafiği

// İYİ: filtre DB tarafında çalışır
var good = await _context.Users
    .Where(u => u.Age >= 18)    // → expression tree DB'ye çevrilecek
    .ToListAsync();             // → sadece gerekli satırlar çekilecek

Kural: ToList, ToArray, First gibi çağrıları sorgunun sonuna bırak — aksi halde istemeden büyük veri çekersin.

AsEnumerable / Cast / AsQueryable: yanlış dönüşümlere dikkat

AsEnumerable() çağrısı sorgu tipini IQueryable → IEnumerable yapar. Bu, sonrasında gelen filtrelerin client-side çalışmasına neden olur.

// Kötü örnek: AsEnumerable sonrası filtre client'ta çalışır
var list = _context.Products
    .Where(p => p.IsActive)        // DB tarafında çalışır
    .AsEnumerable()                // artık IQueryable'dan IEnumerable'a geçildi
    .Where(p => ExpensiveCheck(p)) // ExpensiveCheck C# metodu → client-side çalışır
    .ToList();

Eğer ExpensiveCheck gibi C# metodu DB'ye çevrilemiyorsa, AsEnumerable() veya ToList()'den önce kullanmazsan DB tarafında çalıştırılamaz.

İpucu: Translatible (SQL’e çevrilebilen) fonksiyonlar kullan — EF Core için EF.Functions.Like, DateTime üyeleri, matematiksel operatörler gibi.

Expression Tree — Tam olarak ne oluyor?

IQueryable kullandığında C# derleyicisi, lambda ifadeleri Expression<Func<T,bool>> olarak temsil edilir. Bu ifade ağacı (ağaç yapısı) provider (EF Core) tarafından okunur ve uygun SQL oluşturulur.

// Lambda: u => u.Age > 18
Expression<Func<User, bool>> expr = u => u.Age > 18;
// Bu ifade ağacı provider tarafından parse edilir ve SQL WHERE clause'a çevrilir.

Eğer lambda içinde C# fonksiyonu çağırırsan (örn. IsPrime(u.Id)), provider bunu SQL'e çeviremez — sonuç: ya client evaluation olur ya da EF Core sürümüne göre hata fırlatılır.

Örnek: Custom C# metodu kullanmanın sonucu

bool IsOdd(int x) => x % 2 == 1;

// Kötü: IsOdd C# metodu, EF Core bunu SQL'e çeviremez — client-side evaluation olur veya hata
var q = _context.Numbers.Where(n => IsOdd(n.Value)).ToList();

// İyi: SQL tarafında çalıştırılabilir ifade kullan
var q2 = _context.Numbers.Where(n => n.Value % 2 == 1).ToList();

Performans ölçümü: küçük benchmark

// Stopwatch kullanarak basit ölçüm
var sw = Stopwatch.StartNew();
var a = _context.Users.Where(u => u.IsActive).ToList(); // DB roundtrip
sw.Stop();
Console.WriteLine($"DB sorgu süresi: {sw.ElapsedMilliseconds} ms");

// Eğer ToList()'ü kaldırıp Where'i sonradan uygulasaydık,
// network+memory maliyeti artacaktı.

API/Service katmanında IQueryable döndürmeli miyim?

  • IQueryable döndürmek esnek ama riskli: çağıran katman sorguyu değiştirebilir, provider bağımlılığı sızar (leaky abstraction) ve yanlış kullanım performans sorunlarına yol açar.
  • Güvenli yol: servis katmanında IEnumerable<T> veya DTO döndür ve sorguyu servis içinde optimize et. Eğer gerçekten ihtiyaç varsa, IQueryable döndürmeden önce kullanım sözleşmesini netleştir.

Örnek pattern:

// Rehber: repository/service içinde IQueryable kullan, ama dışa DTO ile materialize et
public async Task<List<UserDto>> GetAdultUsersAsync()
{
    // IQueryable üzerinde filtrelenir ve projection DB tarafında yapılır
    return await _context.Users
        .Where(u => u.Age >= 18)
        .Select(u => new UserDto { Id = u.Id, Name = u.Name })
        .ToListAsync();
}

Özet — Pratik kurallar

  • ToList()/ToArray()/First()'ü gereksiz yere önce çağırma.
  • IQueryable: provider’a (EF Core) ifade ağacı verir — DB tarafında çalıştırılabilir.
  • IEnumerable: bellekte çalışır — büyük tablolar için tehlikeli.
  • AsEnumerable()/AsQueryable() ile tip dönüştürürken niyetini bil.
  • Custom C# metotları kullanma (Where içinde) → SQL’e çevrilemediği için client-side çalışır.
  • Servis/Repository sınırında materialize et (DTO’ya çevir) — IQueryable'ı dışa sızdırma.

Kapanış — Hızlı checklist

  • Sorgular DB tarafında mı çalışıyor? (SQL log / EF Core logging ile doğrula)
  • ToList()'ü erken çağırıyor muyum?
  • Where/Select sırası doğru mu? (Where önce, sonra Select projection)
  • Custom C# fonksiyonları Where içinde yok mu?
  • Service boundary’de IQueryable döndürmüyor muyum?
